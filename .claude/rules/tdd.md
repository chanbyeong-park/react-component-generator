# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 예외를 허용하는 순간 규칙이 아니라 권고가 된다.

---

## 프로젝트별 규칙 우선 조항

이 파일은 **기본값(fallback)** 이다. 현재 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 지침이 존재하면 그쪽을 우선 적용하고 이 파일의 해당 항목을 무시한다.

---

## 적용 기준

**TDD 필수 적용 대상**

- 비즈니스 로직 — 조건 분기, 계산, 상태 전이가 포함된 모든 함수
- API 엔드포인트 — 요청 유효성 검사, 응답 형식, 에러 케이스
- 유틸리티 함수 — 재사용되는 순수 함수
- 버그 수정 — **반드시** 버그를 재현하는 실패 테스트를 먼저 작성

**TDD 불필요 대상**

- 타입 정의 및 인터페이스
- 설정 파일 (vite.config, tsconfig 등)
- 순수 UI 렌더링 (스타일, 레이아웃, CSS 변수)
- SQL 마이그레이션 및 스키마 파일

## RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 작성한 뒤 **반드시 실행하여 실패를 눈으로 확인**한다. 실행하지 않은 테스트는 작성하지 않은 것과 같다.
- 실패 이유가 **"기능이 아직 구현되지 않았기 때문"** 이어야 한다. 문법 오류나 import 누락으로 실패하는 것은 RED가 아니다. 먼저 수정한다.
- 테스트 이름은 "무엇을 할 때 어떻게 동작한다"는 형식으로 작성한다.

### GREEN — 테스트를 통과하는 최소한의 코드

- **테스트를 통과하는 가장 단순한 코드**만 작성한다. 지금 테스트가 요구하지 않는 기능을 미리 구현하지 않는다 (YAGNI).
- 신규 테스트와 **기존 테스트 모두** 통과하는지 확인한다.
- 코드가 지저분하거나 중복이 있어도 GREEN 단계에서는 허용한다. 정리는 REFACTOR에서 한다.

### REFACTOR — 동작 변경 없이 코드 개선

- 중복 제거, 변수명/함수명 개선, 헬퍼 추출만 수행한다.
- **새로운 동작을 추가하지 않는다.** 추가하고 싶은 동작이 생기면 이번 REFACTOR를 마친 뒤 다음 RED로 넘어간다.
- REFACTOR 전후로 모든 테스트가 **GREEN을 유지**해야 한다.

### 반복

REFACTOR가 끝나면 **다음 동작에 대한 RED로 즉시 돌아간다.**

---

## 삭제 강제 규칙

테스트보다 프로덕션 코드를 먼저 작성했다면:

1. 작성한 프로덕션 코드를 **즉시 삭제**한다.
2. RED 단계부터 재시작한다.

**"참고용으로 남겨두는 것"도 금지한다.** 코드가 존재하는 순간 테스트는 그 구현에 맞춰 작성될 위험이 생긴다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순한 함수일수록 테스트 작성 비용이 낮다. 단순함은 면제 이유가 아니라 테스트를 더 쉽게 만드는 조건이다. |
| "나중에 테스트를 추가하겠다" | 나중은 오지 않는다. 구현 직후 코드에 대한 이해도가 가장 높고, 이후 리팩터링 시 테스트가 없으면 안전망이 없다. |
| "시간이 없다" | 테스트 없는 코드는 나중에 더 많은 시간을 디버깅에 쓰게 만든다. 지금의 속도는 빌린 것이다. |
| "이미 작성한 코드를 삭제하면 낭비다" | 삭제하지 않으면 TDD가 아니라 TAD(Test-After Development)다. 규칙을 지키는 비용이 규칙을 어기는 비용보다 낮다. |
| "프로토타입이라서 나중에 다시 쓸 코드다" | 프로토타입은 반드시 버려야 프로토타입이다. 테스트 없이 프로덕션에 올라간 프로토타입은 레거시가 된다. |
